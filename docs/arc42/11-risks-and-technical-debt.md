# 11. Risks and Technical Debt

## 11.1 Risks

| #  | Risk                                                                                                                                 | Impact                                                                                                                                         | Mitigation or next step                                                                                                                                                                 |
|----|--------------------------------------------------------------------------------------------------------------------------------------|------------------------------------------------------------------------------------------------------------------------------------------------|-----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| R1 | **HL7 clone isolation depends on shared internals.** Batch templates are clone sources only, but copies reuse selected dependencies. | Cross-resource state could alter messages despite distinct wrapper contexts.                                                                   | Require passing JSON/XML, concurrent-isolation, and real implementation-guide parity tests for engine or clone-path changes. This documentation review makes no new test-verdict claim. |
| R2 | **HL7 engine upgrades can change validation results.**                                                                               | Referee decisions may change.                                                                                                                  | Pin the engine in `bom`; compare representative golden/regression cases before upgrades and route behavior changes through the responsible governance process.                          |
| R3 | **Input limits can reject workloads larger than their configured values.**                                                           | Previously accepted large batches may now fail during input collection.                                                                        | Document defaults and hard ceilings; tune values only within supported ceilings and validate deployment workloads.                                                                      |
| R4 | **Reports and caches can persist sensitive or identifying data.**                                                                    | Data exposure through report files, package directories, or temporary storage.                                                                 | Treat output and cache locations as sensitive; define permissions, retention, and cleanup for deployments.                                                                              |
| R5 | **No date-source value with only closed profile periods selects no module packages.**                                                | Validation may continue without the intended package set and fail later with a less direct error.                                              | Fail package selection explicitly when a required profile cannot resolve a period; add tests for missing, invalid, and out-of-range dates.                                              |
| R6 | **Unknown terminology can remain a warning and unversioned terminology can resolve unexpectedly.**                                   | An otherwise valid result does not establish full code validation. Cross-release terminology can introduce new failures.                       | Pin terminology versions where possible, test offline coverage, and document exclusions and narrowly scoped transformations. See migration regressions R2 and R4.                       |
| R7 | **Module selection is by name, with first match winning.** No newest-version or engine-compatibility negotiation is performed.       | Multiple releases with the same manifest name can select unintended content. A loadable module can still behave differently with a new engine. | Deploy one intended JAR per module name and record the tested validator/module combination. Retain prior artifacts for rollback.                                                        |
| R8 | **Message policies can hide or downgrade genuine errors.**                                                                           | The processed verdict can be valid despite underlying engine errors. Message wording changes can also make regex rules stop matching.          | Review rationale, constrain match criteria, and test both intended matches and nearby non-matches on every relevant release.                                                            |
| R9 | **Child profile validation is policy-dependent.**                                                                                    | Default validation may not provide the embedded-resource checks expected by a consumer.                                                        | Enable and test `recursiveModePolicy` for the required Bundle/Parameters scenarios. Do not confuse it with module profile extraction or recursive input discovery.                      |
